# Firebase → self-hosted data migration with UUIDv7 ids

**Status:** Proposed, not started · **Recorded:** 2026-10-09
**Starts after:** the application migration ([firebase-to-nestjs-postgres.md](firebase-to-nestjs-postgres.md))
is stable and tested. Until then the schema and the public API may still move, so nothing here is built.
**Replaces:** the current `import:firebase` CLI (`server/src/firebase-import/`), which copies Firestore ids
verbatim into `text` columns.

## Goal

One migration process that connects to a running Localess Firebase install (Firestore + Storage + Auth) and
moves *everything* into a new self-hosted instance, while:

1. every entity gets a new **UUIDv7** primary key, stored in a native Postgres `uuid` column;
2. every reference between entities (inside columns *and* inside content JSON) is rewritten to the new ids;
3. **API tokens keep working unchanged**: the token string customers use stays byte-identical;
4. translation keys and schema names become *values*, not primary keys, so they can be renamed safely;
5. old ids keep resolving on the public API, so customer sites, cached URLs and sent emails don't break.

Exporting / importing a single space between two self-hosted instances stays a UI feature (space Export/Import
tasks). This document is only about the one-off Firebase → self-hosted move.

## Requirements (as agreed)

| # | Requirement |
|---|---|
| R1 | Migration connects to an existing Localess Firebase instance and migrates its data into the new instance. |
| R2 | All ids are migrated to UUIDv7 and every reference is updated to the new ids. |
| R3 | API tokens: `id` = UUIDv7, a separate `token` column holds the Firestore token value; the value customers use stays exactly the same. |
| R4 | Translations: `id` = UUIDv7, separate `key` column holds the translation key. |
| R5 | Schemas: `id` = UUIDv7, separate `name` column holds the schema name (today's schema id). |
| R6 | Content data references (assets, links/references to other contents) are rewritten to the new UUIDs. |

Derived requirements (needed for R1–R6 to be safe):

| # | Requirement |
|---|---|
| D1 | The public API `/api/v1` keeps its contract: translation maps keyed by **key**, content `_schema` and schema `id` as **name**, token strings unchanged. |
| D2 | Old space/content/asset ids keep resolving on the public API (see [Legacy id compatibility](#legacy-id-compatibility)). |
| D3 | The migration is repeatable: re-running it against the same Firebase project updates, never duplicates (needed for a dry run, then a final delta run at cut-over). |
| D4 | Every new id is generated by one function, so new rows and migrated rows have the same shape. |

## Id strategy

### Generation

- `newId()` in `server/src/database/id.ts` returns a UUIDv7 (RFC 9562). It's generated in Node, not with
  Postgres 18's `uuidv7()`, because `DATABASE_URL` may point at Postgres < 18.
- `newId(at?: Date)` takes an optional timestamp. The migration passes the Firestore `createdAt`, so migrated
  rows sort by their real creation time instead of by migration time. The 74 random bits still make it unique.
- Column type becomes native `uuid` for every generated id (16 bytes, time-ordered B-tree inserts).
- `isValidId` / `zId` accept a canonical lowercase UUID; the generic `[A-Za-z0-9_-]{1,128}` pattern is only kept
  where legacy ids are still accepted (D2).

### Per entity

| Entity | New primary key | Kept value | Notes |
|---|---|---|---|
| users | `id uuid` | `legacy_ids` (Firebase uid) | Firebase uid is never exposed publicly. |
| spaces | `id uuid` | `legacy_ids` | Space id is in every public URL and SDK config → D2. |
| contents | `id uuid` (unique per space today, global now) | `legacy_ids` | `content_published.content_id` follows. |
| assets | `id uuid` | `legacy_ids` | `parent_path` (slash-joined folder ids) rewritten; storage key moves to the new id. |
| schemas | `id uuid` | **`name text`**, unique `(space_id, name)` | R5. Public API shows `name` where it showed `id`. |
| translations | `id uuid` | **`key text`**, unique `(space_id, key)` | R4. `translation_published` stays keyed by key. |
| tokens | `id uuid` | **`token text`**, unique | R3. Token lookup becomes `WHERE token = $1`. |
| webhooks | `id uuid` | `legacy_ids` | Webhook secret copied as-is. |
| tasks | `id uuid` | — | Not migrated (history only, files are transient). |
| task_logs, webhook_logs | `bigserial` | — | Unchanged. Webhook logs: migrate or drop (open question). |
| sessions, password reset tokens | hash keys | — | Unchanged, never migrated. |
| settings | `'settings'` | — | Singleton, unchanged. |

Because UUIDs are globally unique, contents and assets can get a single-column primary key `id` again. The
composite `(space_id, id)` key was only there so importing space A's export into space B could reuse ids;
with UUIDs the Export/Import task maps ids instead (see [Space Export/Import](#space-exportimport-ui)).

### New tokens

New API tokens keep the current format: 20 random alphanumerics (~119 bits) in `token`. A UUIDv7 must **not**
be the secret: it has only 74 random bits and leaks its creation time. `validateToken` stays as it is.

### Translations and schemas as values

- `translations.key`: renaming a translation becomes `UPDATE … SET key`, the row id stays. The publish step
  builds `{ [key]: value }`, so the public payload is unchanged.
- `schemas.name`: everything that pointed at a schema id now points at its UUID:
  - `contents.schema_id uuid` (FK to `schemas.id`, replaces `contents.schema text`);
  - `_schema` inside content data nodes;
  - `schemas` arrays of `SCHEMA` / `SCHEMAS` fields;
  - `source` of `OPTION` / `OPTIONS` fields (enum schema).

  Renaming a schema then needs no rewrite. Today `rename` only changes the schema row and leaves those
  references pointing at the old name — this design fixes that as a side effect.
- **Boundary mapping (D1):** the public API and published snapshots must keep `_schema: "<name>"`, because
  customer code switches on it. Publishing (`content-extract.ts`) maps `_schema` UUID → name when it writes
  `content_published`, and the draft content endpoint does the same on read. The DEV_TOOLS `schemas`
  endpoint, the OpenAPI generator and MANAGE schema push work with names and translate at the edge.
- The App API and the Angular app can use UUIDs internally. The frontend already resolves schemas by
  id from `SpaceStore`, so only the display (`name`) changes.

Open question Q1 below: whether `_schema` in *draft* data stores the UUID (consistent, rename-safe) or
the name (simpler, matches published data).

## References to rewrite

The migration builds an id map first (pass 1), then rewrites every reference with it (pass 2).

| Where | Shape | Rewrite |
|---|---|---|
| `contents.schema` | schema name | → `schema_id` (schema UUID) |
| `contents.assets[]`, `links[]`, `references[]` | asset / content ids | map each id |
| `contents.data` (any depth, every locale) | `{ kind: 'ASSET', uri }` | `uri` → asset UUID |
| | `{ kind: 'LINK', type: 'content', uri }` | `uri` → content UUID (`type: 'url'` untouched) |
| | `{ kind: 'REFERENCE', uri }` | `uri` → content UUID |
| | `_schema` on every node | → schema UUID (or name, Q1) |
| | `_id` on every node | **kept**: node ids are local to the document, not references |
| | RICH_TEXT / MARKDOWN strings containing `/api/v1/spaces/{space}/assets/{asset}` URLs | rewritten (optional, Q3) |
| `content_published.data` | same shapes as above, already locale-extracted | rewritten with the same walker; the snapshot is still copied, not rebuilt, because it may differ from the draft |
| `assets.parent_path` | `a/b/c` folder ids | map each segment |
| schema `fields[]` | `schemas[]`, `source` | schema names → schema UUIDs |
| schema `fields[]` | `path` on REFERENCE(S) | **kept**: it's a slug path, not an id |
| `tokens` | Firestore doc id | `token` = doc id, `id` = new UUID |
| `webhooks` | — | new id, secret and headers copied |
| `users.permissions` | permission names | kept (no ids inside) |
| `user_identities` | Google/Microsoft subject from Firebase `providerData` | `user_id` → new user UUID |
| Storage objects | `spaces/{space}/assets/{asset}/original` | copied to the key built from the new ids |
| `spaces.overview` / `progress` | stats | recomputed, not copied |

The rewrite walks the JSON by **shape**, not by schema definition, so it still works for data that no
longer matches its schema. A reference id that isn't in the id map (dangling in Firebase already) is kept
as-is and reported as a warning — the migration never invents or drops data.

## Legacy id compatibility

New ids break every URL that contains an old id unless the old ids keep working. Most important:

- `/api/v1/spaces/{spaceId}/…` — the space id is in every SDK config;
- `/api/v1/spaces/{spaceId}/assets/{assetId}` — asset URLs are embedded in customer sites, CDNs and sent emails;
- `/api/v1/spaces/{spaceId}/contents/{contentId}` — fetch-by-id in customer code.

Proposal: a `legacy_ids` table, written by the migration and read-only afterwards.

```sql
CREATE TABLE legacy_ids (
  entity    text NOT NULL,          -- 'space' | 'content' | 'asset' | 'user' | 'webhook'
  space_id  uuid,                   -- null for space/user
  legacy_id text NOT NULL,          -- Firestore document id / Firebase uid
  id        uuid NOT NULL           -- new UUIDv7
);
CREATE UNIQUE INDEX legacy_ids_lookup ON legacy_ids (entity, space_id, legacy_id) NULLS NOT DISTINCT;
```

It also serves D3: a re-run looks up the existing UUID instead of generating a new one.

Public API behaviour for a non-UUID id:

| Route | Behaviour |
|---|---|
| `spaceId` path segment | Resolve silently (lookup cached in memory). No redirect: tokens and `cv` already handle caching. |
| `assets/:assetId`, `/original`, `/download` | `301` to the canonical UUID URL, so CDNs and browsers converge on one URL. |
| `contents/:contentId` | Resolve, or `301` — same choice as assets (Q2). |
| `links` response, `id` fields in payloads | New UUIDs. Consumers that hard-coded ids in *responses* (not URLs) see a change → release note. |

The lookup only runs when the path segment isn't a UUID, so new installs pay nothing. An env flag
(`LOCALESS_LEGACY_IDS=false`) can switch it off once an install no longer needs it.

Other visible changes to call out in the release notes:

- Webhook payloads carry the new content ids.
- UI deep links (`/features/spaces/<old id>/…`) bookmarked before the migration stop working — the SPA can
  resolve them through an App API endpoint, or we accept it (Q4).

## Migration process

Reuses the Firebase connection that exists today (`server/src/firebase-import/firebase-source.ts`,
`firebase-admin` with a service-account key from env, never argv).

```
npm run localess -- import:firebase --project <id> [--dry-run] [--no-files]
```

1. **Preflight** — connect to Firestore, Storage and Auth; check the target database is empty or was filled
   by an earlier run of the same project (stored in `settings`/`legacy_ids`); print counts per entity.
2. **Pass 1 — id map** — read every document id (users, spaces, schemas, contents, assets, translations,
   tokens, webhooks) and assign a UUIDv7 (`newId(createdAt)`), reusing `legacy_ids` entries from earlier
   runs. Schemas map by name, translations by key, tokens by token value. Nothing is written yet except
   the `legacy_ids` rows.
3. **Pass 2 — rows** — per space, in dependency order: space → schemas → assets (folders before files) →
   contents → published snapshots → translations → published translations → tokens → webhooks. Each row
   goes through the reference rewriter. Writes are upserts keyed by the new UUID, one transaction per
   space, so a failed space can be re-run alone.
4. **Pass 3 — files** — copy Storage objects to the new keys, skipping files whose md5 already matches
   (resumable). Missing files are warnings, not failures.
5. **Users** — Firebase Auth users with password hashes (scrypt params from env or a prompt, as today),
   identities, roles and permissions. Re-hash to argon2id on first sign-in stays as implemented.
6. **Verify** — counts per entity, every reference in contents resolves (or is listed as already dangling
   in Firebase), every token from Firestore authenticates against the new `tokens.token`, sample public API
   responses compared old vs new with ids mapped (optional `--compare-url` pointing at the Firebase install).
7. **Report** — printed and saved as JSON next to the data dir: counts, warnings, dangling references.

Cut-over: dry run → fix warnings → final run in a short write freeze (the delta run is fast because files
and unchanged rows are skipped) → switch DNS → keep the Firebase install read-only until the report is
accepted.

### Space Export/Import (UI)

The UI tasks stay the way to move a single space between self-hosted instances. With UUIDs:

- Export files keep ids (UUIDs) as today, plus schema `name` and translation `key`.
- Import maps every id in the file to a fresh UUID when it doesn't exist in the target space, using the same
  reference rewriter, so importing the same file into two spaces no longer collides.
- Schemas match by `name` and translations by `key` (that's what a user expects when re-importing).
- Exports made by the Firebase version (20-char ids) are accepted the same way: the ids are just "foreign"
  ids that get mapped.

## Implementation plan

Each step is a commit with tests; nothing starts before the application migration is declared stable.

1. **`newId()` → UUIDv7** with optional timestamp; tests for format, ordering and timestamp.
2. **Schema migration**: `uuid` columns; `schemas.name`, `translations.key`, `tokens.token`; `contents.schema_id`;
   single-column keys for contents/assets; `legacy_ids`. The branch has no released installs yet, so the
   Drizzle migrations can be squashed into a fresh initial migration instead of converting data in SQL.
3. **Services and APIs**: token lookup by `token`; translation/schema rename as value updates; publish and
   draft output map `_schema` to name; DEV_TOOLS / MANAGE / OpenAPI by name; frontend models updated.
4. **Reference rewriter** (`server/src/domain/lib/id-rewrite.ts`): pure function `(json, idMap) → json`,
   shape-based, with unit tests per field kind including nested `SCHEMA(S)` nodes and locale variants.
5. **Space Export/Import tasks** use the rewriter (foreign ids → new UUIDs).
6. **Legacy id resolution** in the public API (`spaceId`, assets with 301, contents) + flag; e2e tests with a
   seeded `legacy_ids`.
7. **`import:firebase` rework**: passes 1–7 above; tests against a Firestore emulator fixture (contents with
   every reference kind, nested schemas, folders, published snapshots, V1 and V2 tokens, dangling refs);
   re-run idempotency test.
8. **Docs**: `docs/deployment/migrate-from-firebase.md` rewritten, release notes for the visible changes,
   `docs/v1-api.md` legacy id section.
